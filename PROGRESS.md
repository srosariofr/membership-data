## What's done, in order

1. **Staging layer fixed and documented** — 7 of 8 `stg_*.sql` models had `source()` calls pointing at the wrong names (a leftover from an earlier rename). Fixed, and added `data_tests`/`description` to every staging model (none but one had any before).
2. **`dim_member` cleaned up** — dropped `current_status`/`current_status_start_at` columns from `stg_members`: they were unreliable (the generator hardcodes `current_status = "Active"` at creation time and never updates it — the real status only lives in `member_status_history`). `dim_member` already derived the correct status via a join, so nothing downstream broke. Also removed a no-op `config()` block and added tests/docs.
3. **Payment due dates fixed** — `fct_payments.is_late` was tautologically always `true` (due_date was always constructed to fall before paid_at). Changed the generator (`scripts/generate_data_sources.py`) so `due_date` is derived from `paid_at` with a ~75%-on-time/~25%-late split, for all three payment types. Regenerated `data/*.csv`.
4. **Marts reorganized by domain** — `models/mart/` (flat) → `models/marts/{core,membership,events,finance}/`. Added `fct_applications`, `fct_payments`, `fct_event_attendance`. Unified all mart SQL on one CTE style (entity-named CTEs → `final`), replacing a mix of staging's `source`/`renamed` pattern and ad-hoc styles.
5. **dbt Semantic Layer built** — this was the actual point of the project. Uses dbt-core 1.12's new **colocated** spec (`semantic_model:`/`entity:`/`dimension:`/`metrics:` live inside each mart's own `.yml`, not a separate top-level file). Added a daily `metricflow_time_spine` (2021-01-01 to 2027-01-01).
6. **Two more history facts added** (the accumulating-snapshot + transaction-fact pairing pattern, mirrored from members onto applications):
   - `fct_member_status_history`, `fct_member_monthly_snapshot` (periodic snapshot, member × month, unlocks clean "active members over time" queries)
   - `fct_application_status_history`
7. **`dbt-metricflow` installed** — gives the `mf` query CLI locally (previously only had the `metricflow` engine library, no CLI). All semantic layer metrics validated by cross-checking `mf query` output against direct SQL — exact matches throughout.
8. **Metric descriptions filled in** — the 17 colocated `simple` metrics had no `description:` (only the 3 `ratio` metrics did); spotted via the dbt docs site and fixed.
9. **Project documented** — root `README.md` (was empty) and `dbt/membership_data/README.md` (was the `dbt init` boilerplate) now cover the full stack, data model, setup steps, mart layout, and semantic layer.
10. **Analytics dashboard built** (`dashboard/`) — Flask API (`dashboard/api.py`) + a single self-contained HTML page (`dashboard/static/index.html`, vanilla JS, hand-rolled SVG charts, no build step, no CDN except Google Fonts). Reads *exclusively* through the semantic layer.
    - First cut shelled out to the `mf` CLI per request — worked, but every request paid a ~15-25s cold start (importing dbt-core/metricflow fresh each time). Rewrote to load the `MetricFlowEngine` **once** at Flask startup using the same Python classes `mf` wraps internally (`dbt_metricflow.cli.cli_configuration.CLIConfiguration`, `metricflow.engine.metricflow_engine.MetricFlowQueryRequest`) — brought per-query time down to ~0.5-1s.
11. **BICentric brand theme applied to the dashboard** — colors and logo icon sourced from the user directly (the Google Drive connector couldn't reliably browse the `BICentric_Marca` folder — see [Known issues](#known-issues)). Palette: navy `#001f67`, green `#00823b`, lime `#9dd522` (primary, verified against the actual logo SVG), navy-deep `#061238`, green-soft `#75b148`, teal `#2b595b` (secondary), gray `#f4f4f4` (background). Font switched to **Inter** (Google Fonts). The actual logo's icon mark (3 diagonal bars) is embedded as inline SVG in the header using the real path data, not redrawn. Structure/layout/chart logic untouched — this pass was theme-only, deliberately.
12. **Dashboard restructured into 4 topic tabs** (Memberships / Applications / Events / Payments), each with the same shape: date-range filter → KPI scorecards (ordered by relevance) → evolution line charts → detail tables. Replaced the old single-page layout entirely.
    - `dashboard/api.py`: `/api/query` now accepts `start_date`/`end_date` (`YYYY-MM-DD`), passed to `MetricFlowQueryRequest` as `time_constraint_start`/`time_constraint_end` — this is what powers the per-tab date filter. Invalid dates return 400.
    - Each tab wires its own filter bar (Apply / All-time reset) and lazy-loads its queries on first visit; switching tabs after that just toggles visibility, no refetch until Apply is clicked.
    - Fixed a real bug found while building the "new member registrations by month" chart: `stg_members.sql` never cast `registered_at`/`approved_at` to `timestamp` (every other staging model with a time column does — `stg_membership_applications`, `stg_payments`, `stg_event_attendance`, etc. all cast). The columns were landing as text, so any `group_by=metric_time__month` query against `dim_member` failed with a `DATE_TRUNC(unknown, text)` Postgres error. Fixed the cast and reran `dbt build --select stg_members+` (54/54 pass).
    - Verified all 4 tabs end-to-end in-browser (scorecards, charts, tables, date-filter apply + reset) after restarting the Flask process to pick up both the API change and the rebuilt `dim_member`.
13. **Hover tooltips added to the line charts** — `lineChart()` in `dashboard/static/index.html` now draws one invisible hit-column per x-index; hovering shows a shared tooltip (title + each series' value + color swatch), enlarges the point(s) at that index, and draws a dashed vertical guide line. Shared `getTooltip()`/`positionTooltip()` helpers so the same tooltip element is reused across charts (and later reused by the pie charts in item 14).
14. **Memberships tab replaced with a "Member Base" tab** — no longer an evolution-over-time view; it's a snapshot analysis of the current membership roster with 6 dimension filters (Industry, Tenure, Age Range, Gender, Status, Position), scorecards (Total + one per status), a pie chart per dimension (all cross-filtered together), and a member-level detail table. No date filter, per the user's request — this is a current-state view, not a time series.
    - **New `dim_member` columns**: `age_range` and `tenure_range`, computed in `dim_member.sql` from `birth_date`/`approved_at` vs `current_date` (bucketed: age in `Under 25/25-34/35-44/45-54/55-64/65+`, tenure in `Under 1 year/1-3 years/3-5 years/5+ years`). Declared as categorical dimensions in `dim_member.yml`, same pattern as every other dimension in the repo — computed at dbt-build time, not live at query time, consistent with the mart being a table, not a view.
    - **`name`/`email` promoted to dimensions** on `dim_member` (previously plain columns, not queryable via MetricFlow `group_by`). This is what makes the member-level detail table possible entirely through the semantic layer: `group_by` on enough dimensions to be unique per member (name, email, status, industry, profession, gender, age_range, tenure_range, country) with `metrics=members` (count) as a dummy 1-count column yields exactly one row per matching member — no raw SQL needed for the "list actual members" requirement.
    - **"Position" filter uses `profession`** — the dataset has no job-title/hierarchy field (CEO/Manager/Analyst); the user chose (via `AskUserQuestion`) to reuse the existing `profession` field (Software Engineer, Lawyer, Accountant, etc.) as the closest proxy rather than fabricate new synthetic data and regenerate `data/*.csv` (which has no fixed seed — would've reshuffled every number on every other tab too).
    - **`dashboard/api.py` gained a `filters` param**: `dim1:value1|dim2:value2`, translated server-side into MetricFlow `where_constraints` (`{{ Dimension('dim') }} = 'value'`). Dimension names validated against the same `IDENTIFIER_RE` used for `metrics`/`group_by`; values are only ever compared for equality inside a quoted literal, so the only escaping needed is doubling embedded single quotes. Verified cross-model filtering works (e.g. filter on `company__industry`, group by `member__gender` — joins through the `company` entity on `dim_member`).
    - **New `pieChart()` renderer** in `index.html` (hand-rolled SVG arcs, same no-library approach as `lineChart()`) with the same hover-tooltip treatment as the line charts (slice highlight + tooltip showing label/value/%). Later converted to donuts — see item 15.
    - Detail table capped at 500 rows (`limit=500` in the query) with a "showing first 500" note when truncated, and wrapped in a `max-height:480px; overflow-y:auto` scroll container with a sticky header — without this the unfiltered table (3,317 rows) blew the page out to ~19,000px tall.
    - Verified end-to-end in-browser: filter selection cross-updates scorecards + all 6 pies + the detail table together (tested filtering Industry=Technology: total dropped 3,317→370 consistently everywhere), and resetting a filter back to "All" restores the full count.
15. **Member Base tab refined** (user feedback across several small requests):
    - **Pies → donuts**: `pieChart()` now draws an annulus (`outerR=60, innerR=36`) via a new `donutArcPath()` helper instead of full wedges, with the running total centered in the hole. Single-category case draws two concentric `<circle>`s (colored ring + white hole) since a single donut "arc" degenerates.
    - **Self-exclusion + highlight on the donuts**: each donut's query now excludes *its own* dimension from the active filter set (`buildFiltersString(filters, excludeKey)`) — filtering Status=Active no longer collapses "By Status" into a meaningless single 100% ring; it still shows the full distribution, with the Active slice/legend row bolded and the rest dimmed to 35% opacity (`pieChart`'s `highlightLabel` option). All *other* donuts still fully respect the Status filter — self-exclusion is scoped to a chart's own dimension only.
    - **Percentages on the status scorecards**: each status card now shows `count · pct%` of the currently filtered total (e.g. "1,685 · 50.8%"), via `kpiCard`'s existing `sub` param.
    - **Company info added**: `dim_company.company_name` promoted to a queryable dimension (same pattern as `dim_member.name`/`email` in item 14) — rebuilt with `dbt build --select dim_company` (8/8 pass). Added a "Top Companies by Member Count" table (`group_by=company__company_name`, `limit=20`, respects all active filters) above the member detail table, and added a "Company" column to the member detail table itself.
    - Explicitly **not** done (deferred at user's request): multi-select filters. Would need array-valued filter state, an `IN (...)` where-clause path in `api.py`'s `_parse_filters` (currently only `=`), a real custom multi-select UI (native `<select multiple>` was judged too clunky), and `highlightLabel` becoming a list. Flagged as real but moderate work if revisited.

## Known issues

- **Google Drive connector is unreliable in this environment.** `search_files` only reliably returns results for one specific query it seems to have cached (`title contains 'Bicentric' or title contains 'BICentric'`); any other query — different keywords, `parentId` filtering, pagination (`pageToken`), or `pageSize` — fails with "Operation is not implemented, or supported, or enabled." Could not browse the `BICentric_Marca` folder directly; the user ended up pasting the color palette and the logo SVG into the chat instead. If Drive access is needed again, expect this same failure mode and don't sink time into query-string guessing — ask the user to paste/upload instead.
- **`mf` CLI needs `DBT_PROFILES_DIR` set explicitly on Windows** (documented in README) — it doesn't resolve `~/.dbt` the way the `dbt` CLI does.
- **`mf`'s emoji crash was patched directly in `.venv/Lib/site-packages/dbt_metricflow/`** (stripped emoji/non-cp1252 characters from `main.py`, `tutorial.py`, `utils.py` — Windows' default console codepage can't encode them, causing a `TypeError` inside `halo`/`colorama`). This is **not part of the repo** (site-packages isn't tracked) and **will be lost if `dbt-metricflow` is reinstalled or upgraded**. The README documents the `PYTHONIOENCODING=utf-8 PYTHONUTF8=1` workaround as the fallback if that happens.
- The data generator's `random` module isn't seeded (only Faker is) — regenerating `data/*.csv` produces a different dataset each time. Documented in the README; not considered a bug worth fixing unless reproducibility becomes important.

## Backlog / ideas not yet started

Roughly in the order they came up in conversation, not necessarily priority order:

- **Saved queries** — name the dashboard's repeated query shapes as `saved_queries` in the semantic layer YAML instead of hardcoding metric/group-by lists in `dashboard/static/index.html`.
- **Derived/cumulative metrics** — everything so far is `simple` or `ratio`. Nothing uses MetricFlow's `derived` (e.g. month-over-month revenue growth using `offset_window`) or `cumulative` (running-total revenue) metric types yet. Churn rate (cancellations this month ÷ active members last month) would be a good first derived metric to try, since it needs a period-over-period comparison.

Worth revisiting once dbt-core ships a stable (non-`b3`) 1.12 release, and possibly hosting the generated static docs site on GitHub Pages instead of requiring anyone to run it locally.
- **Dashboard visual polish**: the brand theme (colors/font/logo), the 4-tab restructure, hover tooltips, and the Member Base tab are all done; still worth checking in on whether more brand assets exist (`BICentric_Marca` — logo lockups, secondary marks, spacing rules) beyond what was pasted into chat.

16. **Lightdash POC** — explored self-service BI on top of the existing dbt Semantic Layer, as an alternative/complement to hand-building views in the Flask dashboard.
    - **No dbt Cloud needed.** The common assumption is that "dbt Semantic Layer" tools require dbt Cloud's hosted Semantic Layer API, but Lightdash's actual mechanism is different: `lightdash deploy` compiles the dbt project locally (same as `dbt build`/`mf`) and translates the supported subset of MetricFlow metrics (`simple`, `ratio`, `derived`) into Lightdash's own metric catalog. Confirmed end to end against this project's fully local, non-Cloud dbt-core setup.
    - **Infra**: `lightdash/docker-compose.yaml` — a separate Docker stack from the project's own `docker-compose.yaml` (Lightdash needs its own Postgres for app metadata, kept apart from `msd_postgres`). One real surprise vs. plan: this version of Lightdash **requires S3-compatible storage unconditionally** (`ParseError: S3-compatible storage is required` on boot) even though the official docker-compose's `minio`/`headless-browser` services looked skippable for a metrics-only POC — added a second, separate MinIO (`msd_lightdash_minio`, ports `9010`/`9011` to avoid colliding with the project's own `msd_minio`) plus a one-shot `minio/mc` `createbuckets` service to provision the bucket automatically.
    - **CLI auth**: `npm install -g @lightdash/cli`, then `lightdash login <url> --token <personal-access-token>` (token generated in the web UI). Both `lightdash login` and `lightdash deploy` print **zero output** and appear to hang when stdin isn't closed — they're waiting on stdin, not actually stuck. Fix: append `< /dev/null` (and `CI=true` didn't hurt but wasn't the actual fix) to any non-interactive invocation from a script/agent.
    - **SSL blocker**: `lightdash deploy --create` failed with `The server does not support SSL connections` — `postgres:16` (this project's warehouse container) has SSL off, and Lightdash's own warehouse-catalog fetch step for the CLI defaults to requiring it. Setting **"SSL mode" to `disable` in the Lightdash web UI's project settings did not fix the CLI's own connection** — the CLI builds its warehouse connection straight from `~/.dbt/profiles.yml`, which had no `sslmode` key at all. Fix: added `sslmode: disable` directly to the `dev` target in `~/.dbt/profiles.yml` (outside the repo). Two separate SSL settings that look like they should be the same thing aren't, for this CLI-connection-type project.
    - **Scope correction**: the very first successful deploy pushed the **entire dbt project** (18 explores — all 8 `stg_*` staging views plus the 9 marts + time spine), because `deploy --create`'s project-creation flow doesn't ask which models to include. Fixed with `lightdash deploy --select path:models/marts` (dbt selection syntax), which cut it down to the intended 10 explores (marts only, no staging).
    - **Metric translation confirmed working**: all **20 MetricFlow metrics translated with zero errors** ("Translated 20 MetricFlow metric(s) into Lightdash metrics") — including the 3 `ratio` metrics (`approval_rate`, `late_payment_rate`, `event_attendance_rate`), which was the main risk flagged going in (Lightdash's MetricFlow integration is beta and silently drops ratio/derived metrics that cross semantic models — none of these three do, so all three came through).
    - **Real limitation found**: the MetricFlow→Lightdash beta translation does **not** turn MetricFlow `entity` relationships into Lightdash joins between explores. Opening `fct_applications` initially showed only its own fields (`company_id` as a raw FK, not a related `dim_company` field) — no way to combine dimensions/metrics across tables until joins were added by hand. Fixed by adding Lightdash-specific `meta.joins` blocks (dbt-`meta`-level config, separate from the `semantic_model`/`entity` blocks MetricFlow uses) to 6 mart YAMLs: `fct_applications`, `dim_member`, `fct_event_attendance`, `fct_payments`, `fct_member_status_history`, `fct_application_status_history`, `fct_member_monthly_snapshot` — one join per real foreign key, wiring every fact table to its dimension(s) (and `fct_application_status_history`/`fct_payments` to `fct_applications`, a fact-to-fact join). Confirmed working after redeploy: joined fields from related tables now appear as their own sections in the field picker.

## Known issues

- **Google Drive connector is unreliable in this environment.** `search_files` only reliably returns results for one specific query it seems to have cached (`title contains 'Bicentric' or title contains 'BICentric'`); any other query — different keywords, `parentId` filtering, pagination (`pageToken`), or `pageSize` — fails with "Operation is not implemented, or supported, or enabled." Could not browse the `BICentric_Marca` folder directly; the user ended up pasting the color palette and the logo SVG into the chat instead. If Drive access is needed again, expect this same failure mode and don't sink time into query-string guessing — ask the user to paste/upload instead.
- **`mf` CLI needs `DBT_PROFILES_DIR` set explicitly on Windows** (documented in README) — it doesn't resolve `~/.dbt` the way the `dbt` CLI does.
- **`mf`'s emoji crash was patched directly in `.venv/Lib/site-packages/dbt_metricflow/`** (stripped emoji/non-cp1252 characters from `main.py`, `tutorial.py`, `utils.py` — Windows' default console codepage can't encode them, causing a `TypeError` inside `halo`/`colorama`). This is **not part of the repo** (site-packages isn't tracked) and **will be lost if `dbt-metricflow` is reinstalled or upgraded**. The README documents the `PYTHONIOENCODING=utf-8 PYTHONUTF8=1` workaround as the fallback if that happens.
- The data generator's `random` module isn't seeded (only Faker is) — regenerating `data/*.csv` produces a different dataset each time. Documented in the README; not considered a bug worth fixing unless reproducibility becomes important.
